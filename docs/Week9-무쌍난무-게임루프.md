## 2. 무쌍난무 설계

### 2.1 한 줄 요약
**적을 벨수록 게이지가 차고, 가득 차면 발동 — 일정 시간 동안 무적으로 광역 타격을 연타한다.**

### 2.2 데이터 흐름

```
[적 사망] → DeathEventQueue → DeathEventBridge(유일 소비자) → 킬 수
                                          │
                                          ▼
                                  MusouGaugeBridge (게이지 충전)
                                          │  가득 참 + 입력(R)
                                          ▼
                          발동: N회 반복 AttackRequest(광역) + 무적 + 셰이크
                                          │
                                          ▼
                              [ECS] AttackResolveSystem (기존 그대로)
```

### 2.3 결정 기록 (ADR)

**① 게이지는 GameObject(플레이어)가 소유한다**
- **이유**: 게이지는 입력·UI·연출과 붙어 있는 **플레이어 상태**다. ECS는 "누가 맞았나"만 알면 되고, 발동 결과는 이미 있는 `AttackRequest`로 충분하다. 아키텍처 원칙(플레이어=GO, 군중=ECS)에도 맞는다.
- 트레이드오프: ECS 시스템이 게이지를 못 읽는다 → 필요해지면 `PlayerState`에 필드를 추가(현재는 불필요).

**② 충전은 `DeathEventBridge`의 킬 수를 읽어서 한다 (큐를 직접 소비하지 않는다)**
- **이유**: `NativeQueue`는 **소비하면 사라진다.** `DeathEventBridge`가 이미 매 프레임 전부 드레인하므로, 게이지가 큐를 또 읽으면 킬카운트와 서로 이벤트를 뺏어 **둘 다 가끔 틀린다.** Week 8 히트스톱 트리거에서 내린 것과 **같은 원칙**: *큐 소비자는 1명, 나머지는 그 결과를 읽는다.*
- 구현: `DeathEventBridge.KillCount`(공개) → 게이지는 프레임당 증가분만큼 충전.

**③ 발동기는 "새 기술"이 아니라 광역기의 반복이다**
- **이유**: Week 3의 *"공격 = 데이터"* 설계 덕에 `AttackRequest`는 반경·데미지·넉백·경직을 파라미터로 받는다. 무쌍난무 = **큰 파라미터의 요청을 짧은 간격으로 여러 번** 쏘는 것 → 새 시스템 0개.
- 부수 효과: 밸런싱이 인스펙터 숫자 놀음이 된다(펄스 수·간격·반경·데미지).

**④ 발동 중 무적(i-frame)은 소비 지점에서 막는다**
- **이유**: 적의 공격은 `PlayerDamageQueue`에 쌓이고 `PlayerHealthBridge`가 소비한다. **큐는 계속 비우되 HP만 안 깎으면** 되므로, 소비 지점의 플래그 하나로 끝난다(큐가 안 비면 무적 해제 순간에 밀린 데미지가 한꺼번에 들어온다 — 반드시 비우면서 무시).
- 회피(Dodge)의 i-frame도 이 플래그를 그대로 쓴다 → §4에서 재사용.

### 2.4 파라미터 (초안 · 튜닝 대상)

| 항목 | 값 | 비고 |
|---|---:|---|
| 최대 게이지 | 100 | |
| 킬당 충전 | 1.5 | 병사 1300 기준 한 판에 여러 번 발동 가능 |
| 리더 킬 보너스 | +15 | 리더 처치 = 큰 보상(현재는 킬 수만 읽으므로 후속) |
| 발동 키 | **R** | 좌클릭 콤보·우클릭 광역기와 겹치지 않음 |
| 지속 | 2.4s | |
| 펄스 | 8회 (0.3s 간격) | |
| 펄스 반경 | 18 | 광역기(25)보다 좁고 자주 |
| 펄스 데미지 | 120 | 병사(100) 즉사, 엘리트(300) 3펄스 |
| 무적 | 지속 전체 | |

## 3. 게임 루프

- **승리**: **리더 11기 전멸**(병사는 무한 스펙터클). 편성이 리더 중심이라 목표가 자연스럽다.
- **패배**: 플레이어 HP 0 (이미 `PlayerState.IsDead` 존재).
- **UI**: 남은 리더 수 · 결과(승/패) · 리트라이(씬 리로드).

### 3.1 결정 기록 (ADR) — 게임 상태를 누가 소유하나

> **결정: ECS가 소유한다.** `StageState` 싱글톤을 시스템이 갱신하고, UI 브릿지는 **읽어서 그리기만** 한다.
> 후보 (a) "UI 브릿지가 매 프레임 `EntityQuery(LeaderTag).CalculateEntityCount()`로 직접 판정"은 폐기.

**채택 이유**
1. **게임 상태는 규칙이고, 규칙은 시뮬레이션 레이어에 있어야 한다.** UI가 승리 조건을 판정하면 규칙이 늘어날 때(웨이브·제한시간·목표 다변화) UI와 규칙이 얽혀 유지보수가 무너진다.
2. **다른 시스템이 같은 상태를 읽어야 한다.** 클리어 시 스폰 정지·적 공격 중단·연출 트리거는 전부 ECS 쪽 일이다. (a)라면 ECS가 GO를 되참조해야 해서 이 프로젝트가 지켜온 단방향 경계가 깨진다.
3. **판정 시점이 명확하다.** SystemGroup 안에서 정해진 순서에 평가되므로 프레임 경계에서 애매해지지 않는다.
4. **검증이 쉽다.** 싱글톤 하나만 읽으면 상태를 알 수 있다(지금까지 해온 헤드리스 검증 방식과 동일).

**트레이드오프**: 컴포넌트+시스템 파일이 2개 늘고, UI는 싱글톤을 읽는 코드가 필요하다. 규칙이 영원히 하나뿐인 프로토타입이라면 (a)가 더 빠르지만, 웨이브·시간제한이 로드맵에 있으므로 (b)가 맞다.

### 3.2 데이터 모델

```
enum StagePhase : byte { Playing, Cleared, Failed }

struct StageState : IComponentData {
    StagePhase Phase;
    int   LeadersRemaining;   // 남은 리더(승리 조건)
    int   LeadersTotal;       // 시작 시 리더 수(UI 표시용)
    float Elapsed;            // 경과 시간(클리어 기록)
}
```

- `StageStateSystem`: Playing일 때만 갱신 → 리더 수 세고, 0이면 `Cleared`, `PlayerState.IsDead`면 `Failed`.
- UI 브릿지: 싱글톤을 읽어 "남은 장수 3/11" 표시, Cleared/Failed면 결과 패널 + 리트라이(씬 리로드).

## 4. 회피 (Dodge)

### 4.1 조작·수치 (초안)

| 항목 | 값 | 비고 |
|---|---|---|
| 입력 | **Space** | Shift는 걷기 토글로 이미 쓰임 |
| 대시 거리/시간 | 5m / 0.25s (≈20m/s) | 방향 = WASD 입력, 없으면 캐릭터 정면 |
| 무적 | 대시 시간 + 0.05s 여유 | |
| 쿨다운 | 0.8s | |
| 공격 중 사용 | 허용(공격 캔슬) | 무쌍류 손맛 — 콤보에 갇히지 않게 |

### 4.2 결정 기록 (ADR) — 무적을 bool이 아니라 **만료 시각**으로

> **결정: `PlayerHealthBridge.IsInvulnerable`(bool) → `AddInvulnerability(duration)` + 내부 만료 시각.**

- **이유**: 무적의 소유자가 **둘 이상**(무쌍난무·회피)이 되는 순간 bool은 깨진다. 무쌍난무 무적(2.4s) 중에 회피(0.3s)를 쓰면, 회피가 끝나며 `false`로 꺼서 **남은 2초의 무적이 취소**된다. 만료 시각을 `max()`로 합치면 어느 쪽도 남의 무적을 끄지 않는다.
- 부수 효과: 끄는 코드가 사라져 `OnDisable`에서의 정리도 불필요해진다(시간이 알아서 만료).
- 같은 원리를 이미 히트스톱에서 썼다(`HitStop.Remaining = max(현재, 신규)`) — **겹치는 효과는 시간으로 합친다**가 이 프로젝트의 패턴.

### 4.3 구현 위치

- **대시 이동은 `PlayerController` 안**: 이동을 소유한 곳이 거기다. 별도 컴포넌트로 빼면 같은 프레임에 둘이 `transform`을 밀어 충돌한다.
- 무적 요청은 `PlayerHealthBridge.AddInvulnerability(대시시간 + 여유)` 한 줄.
- 애니는 전용 회피 클립이 없으므로 우선 이동만(폴리싱 백로그).

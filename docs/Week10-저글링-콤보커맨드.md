# 1. 띄우기 (Airborne) — 완료

## 1.1 한 줄 요약
**우클릭 공격이 적을 수직으로 띄우고, 중력으로 떨어져 착지한다.** 공중에 뜬 적은 지상 행동(추적·공격)을 하지 않는다.

## 1.2 데이터 흐름 — 새 파이프라인이 아니라 **수직 성분 한 칸 추가**

```
AttackRequest.LaunchY   (플레이어 GO가 파라미터로 지정)
   → AttackResolveSystem  … 반경 내 적의 DamageEvent에 LaunchY 복사   [기존 시스템]
   → DamageApplySystem    … LaunchY>0 이면 Airborne.VelocityY 부여 + 활성
   → AirborneSystem       … 중력 적분, y<=0에서 착지·해제              [신규]
```

계획서(§E)가 예고한 *"`DamageEvent`에 넉백 이미 있음 → 수직 성분만 추가"* 가 그대로 성립했다. 새 공격 파이프라인은 만들지 않았다.

## 1.3 결정 기록 (ADR)

**① `Airborne`은 Enableable 컴포넌트**
1만 마리 중 소수만 떠 있다. 컴포넌트를 붙였다 뗐다 하면 청크 이동(구조 변경)이 발생하므로, **비트만 토글**한다 — Week 4에서 `DeadTag`로 수치 검증했던(Enableable 31.7ms vs AddComponent 42.3ms) 바로 그 패턴의 재사용.

**② Y 좌표의 소유자는 `AirborneSystem` 하나**
이번 작업의 핵심 계약. 다른 어떤 시스템도 Y를 건드리지 않는다(§1.4에서 이 계약을 어긴 곳을 전부 잡았다).

**③ 띄우기도 `knockbackFactor`를 곱한다**
거대 리더(보스·엘리트)는 넉백 면역(계수 0)이므로 **띄워지지도 않는다**. 무게감이 일관되고, 별도 플래그가 필요 없다.

## 1.4 ⚠️ 이번에 드러난 함정 3개

세 개 모두 *"적은 항상 바닥(y=0)"* 이라는 **암묵적 전제**가 깨지면서 노출됐다. 계획서가 이 작업을 "가장 큰 단일 조각"으로 표시한 이유가 이것이다.

| # | 증상 | 원인 | 해결 |
|---|---|---|---|
| **1** | **데미지가 아예 안 들어감**(띄우기는커녕) | `DamageApplyJob` Execute에 `Airborne`(enableable)을 받자, **꺼져 있는(=지상) 적이 쿼리에서 통째로 제외**됐다. IJobEntity는 enableable이 비활성인 엔티티를 기본 제외한다 | `[WithPresent(typeof(Airborne))]` — `DeadTag`에 이미 같은 이유로 붙어 있었다. `DeathSystem` 쿼리도 `.WithPresent<Airborne>()` |
| **2** | 착지한 적이 **다시 떠오름**, y가 플레이어 y로 수렴 | `MovementSystem`이 `normalize(Target - Position)`으로 **3D 추적** → 루트모션으로 살짝 떠 있는 플레이어를 Y까지 따라갔다 | 이동을 **수평만**으로(`toTarget.y = 0`) |
| **3** | 아무도 안 띄웠는데 maxY가 계속 증가(5.5m까지) | `SeparationJob`의 밀어내기가 **3D** → 밀집한 좀비가 서로를 **위로** 밀어 올리고, 한 번 뜨면 증폭 | 밀어내기도 **수평만**(`diff.y = 0`). 넉백 방향도 같은 이유로 수평화(수직은 `LaunchY` 담당) |

> **교훈**: 새 축(Y)을 도입할 때 진짜 비용은 신규 시스템이 아니라 **기존 시스템들이 갖고 있던 암묵적 전제를 찾아내는 것**이다. "경직 때의 확대판"이라던 계획서의 표현이 정확했다.

## 1.5 수치·검증

| 항목 | 값 |
|---|---|
| 우클릭 `LaunchY` | 9 m/s (정점 ≈ 1.84m, 체공 ≈ 0.82s) |
| 중력 | 22 m/s² (실제보다 세게 — 공중 콤보가 늘어지지 않게) |
| 체공 중 | 추적·공격 금지, 피격 모션 재생, 사망해도 착지 후 쓰러짐 |

**실측**: 649마리 동시 상승(프레임당 상승폭 0.17→0.10으로 감속 = 중력 정상), 정점 1.75m(이론 1.84m), 3초 후 **전원 착지·`maxY=0.00` 유지**(공중 잔류 0), 데미지 파이프라인 회귀 없음.

# 2. 콤보 커맨드 (진삼국무쌍식) — **보류 · 설계만**

> 약공격 몇 타 뒤에 강공격을 넣느냐에 따라 파생기가 달라지는 시스템. 지금은 구현하지 않는다.

## 2.1 쓸 수 있는 애니 자산 (조사 완료)

플레이어(HornedKnight)는 **ARPG_Warrior 클립을 Humanoid 리타깃**해서 쓰고 있다 → ARPGPack 전체를 쓸 수 있다.

| 용도 | 클립 |
|---|---|
| 약공(현재 사용 중) | `Attack_Combo1~4` |
| 강공 | `Attack_Heavy1_Start` · `Attack_Heavy2` · `Attack_HeavyB` · `Attack_Heavy_Mid`(+Turn45/90 변형) |
| 추가 콤보 | `Attack_ComboB1~B5` |
| 공중 | `Attack_Airborne_Start/Mid/End` · `Attack_Airborne_Landing` |
| 기타 | `Attack_Dodge_to_Combo1`(회피 후 콤보 파생), `Execute`(처형) |

## 2.2 커맨드 표 (초안)

| 커맨드 | 파생 | 효과 (기존 `AttackRequest` 파라미터 조합) |
|---|---|---|
| 강공 단독 | Heavy1 | 정면 강타 |
| 약1 → 강 | Heavy1_Start | **띄우기**(LaunchY 크게) |
| 약2 → 강 | Heavy2 | 넓은 넉백 |
| 약3 → 강 | HeavyB | 광역 다단 |
| 약4 → 강 | ComboB5 | 피니시(강한 띄우기 + 넉백) |

→ **여기서도 새 전투 시스템은 0.** 파생기는 "다른 숫자를 든 `AttackRequest`"일 뿐이다(Week3 "공격=데이터"의 네 번째 배당).

## 2.3 착수 전에 정해야 할 것

1. **타격 판정을 어떻게 낼 것인가** — 지금은 클립에 박힌 Animation Event(`OnAttackStart/End`, 본 이름·위력 파라미터)에 의존한다. 새 강공 클립엔 이벤트가 없다.
   - **(A) 코드 타이밍**: 강공은 단발이니 트리거 후 고정 딜레이(예: 0.25s)에 `AttackRequest` 1발. 클립 편집 불필요, 즉시 가능. 대신 클립마다 히트 타이밍을 손으로 맞춰야 한다.
   - **(B) 이벤트 추가**: 각 강공 클립에 이벤트를 심어 기존 방식과 통일. 정확하지만 클립 수만큼 편집 필요.
2. **우클릭을 강공으로 돌릴지** — 현재 우클릭 = 광역기(+띄우기). 광역 역할은 무쌍난무가 가져갔으니 우클릭을 **강공(파생기 입력)** 으로 바꾸는 게 자연스럽다. 그러면 지금의 우클릭 띄우기는 "약1 → 강" 파생으로 이동한다.
3. **입력 버퍼·타이밍 윈도우** — 콤보 입력 선입력(버퍼) 허용 시간, 파생 가능 구간(클립의 몇 %까지).
4. **Animator 상태 추가** — 강공 상태 5개 + 전이 조건(`Attack`/`Heavy` 트리거 + `ComboStep` int).

## 2.4 예상 작업량

| 파트 | 규모 |
|---|---|
| Animator 상태·전이 추가 | 중 (스크립트로 자동 생성 가능) |
| 입력·콤보 상태기(MonoBehaviour) | 중 |
| 히트 판정 배선(A안이면 작음) | 소~중 |
| 파생별 파라미터 튜닝 | 소 |
